# Capability, Module & Provider Registry

1stStep OS maintains live registries rather than hard-coding one vendor forever. Architecture: ADR-014. Schemas: `schemas/0.1.0/`.

| Registry | File | Status |
|---|---|---|
| Capabilities (301) | `capabilities/registry.json`, generated by `npm run registry` from `.project-os/capability-taxonomy.json` + the classification in `tools/build-capability-registry.mjs` | Cycle 0 |
| Modules (22) | `modules/registry.json` | Cycle 0 |
| Tool providers | `ToolProvider` schema; registry file added at M3 with verified entries | Schema only |
| Model providers | `ModelProvider` schema; registry file added at M3 with verified entries | Schema only |

`capabilities/<domain>/*.md` files are **stubs** (`status: STUB`) holding the generator contract headings. They carry no authority beyond their registry entry and are filled when a capability's generation phase is reached.

## Provider entry requirements (preserved; now schema-enforced)

Each provider/tool/model entry records:

- capability
- provider
- model/tool ID
- quality tier
- cost/pricing basis
- latency
- input/output limits
- commercial-use/licensing notes when known
- privacy/data-retention notes
- API/connector availability
- auth requirements
- strengths
- weaknesses
- last verified
- fallback
- supported automation level

Facts about third parties are assessments with evidence. Unverified pricing or terms are never treated as known, and a model without a KNOWN price cannot be ACTIVE.

The router selects on quality, cost, privacy, latency, availability, project constraints and user preference, using the order in `tooling/COST_FIRST_ROUTER.md`.

## Module & capability selection algorithm (deterministic)

`selectModules(profile, moduleRegistry, capabilityRegistry, platformPhase) → { selected, deferred, decisions, trace }`

1. **Normalize.** Read each condition field from the profile. The field state is the assessment `status`: KNOWN, UNKNOWN, NOT_APPLICABLE or DECLINED.
2. **Evaluate conditions** (modules are processed in id order):
   - KNOWN:
     - `INCLUDES_ANY` → value ∩ values ≠ ∅
     - `EXCLUDES_ALL` → value ∩ values = ∅
     - `IN` → scalar ∈ values
     - `IS_TRUE` / `IS_FALSE` → boolean equality
   - NOT_APPLICABLE → condition is **false** for every operator.
   - UNKNOWN → apply the module's `onUnknown`:
     - `EXCLUDE` → false
     - `INCLUDE` → true
     - `RAISE_DECISION` → false, plus emit a decision for that field
   - DECLINED → like UNKNOWN, but the emitted decision is non-blocking and recorded as an ASSUMED assumption once the user confirms "decide later".
3. **Applicability.** `ALWAYS` → match. `RULES` → every `all` condition is true **and**, if `any` is present, at least one `any` condition is true. Match reason `RULE_MATCH`.
4. **User additions.** Modules added explicitly by the user get reason `USER_ADDED`. Capability requests only influence selection through module rules on `capabilityRequests`.
5. **Dependencies.** Add transitive `dependsOn` with reason `DEPENDENCY`. If a dependency's own rules evaluate to **false on KNOWN data** (e.g. `payments.needed = false` but `ecommerce` needs `payments`), emit a blocking `DEPENDENCY_CONTRADICTS_PROFILE` decision instead of silently adding it.
6. **Conflicts.** If the final set contains a declared conflict pair, return `MODULE_CONFLICT`. Nothing is resolved silently.
7. **Phase deferral.** Modules with `phase` later than `platformPhase` move to `deferred` (reason `PHASE_NOT_AVAILABLE`).
8. **Capabilities.** The union of selected modules' capabilities is filtered to `generationPhase ≤ platformPhase`. A capability with `consentRequired` is included as guidance only; execution needs consent (reason `CONSENT_REQUIRED` in manifest when relevant).
9. **Decision de-duplication.** Decisions are keyed by profile field. A field decision is `blocking` if any module raising it declares `riskFactors`, or if it is the `mode` field.
10. **Output ordering.** Modules and capabilities sorted by id; decisions sorted by field; `trace` lists each evaluated condition and its outcome.

**Required tests (M1):** a golden fixture per module covering match, UNKNOWN per `onUnknown`, NOT_APPLICABLE, DECLINED, dependency add, dependency contradiction, conflict, phase deferral. Plus a property test: shuffling registry order yields identical output.

## Registry integrity (enforced now by `npm run check`)

- **Capability registry:** ids equal the taxonomy; each capability has exactly one stub doc; dependencies exist, are acyclic and never point to a later generation phase; execution phase ≥ generation phase.
- **Module registry:**
  - unique ids
  - dependencies exist, are acyclic and never point to a later module phase
  - conflicts are declared on both sides
  - capability, agent and gate references exist
  - each required file is owned by one module
  - condition values exist in the profile schema enums
  - every capability is reachable through at least one module

## Adding a capability or module

1. Add the capability to `.project-os/capability-taxonomy.json` and create its stub doc.
2. Classify it in `tools/build-capability-registry.mjs` (the build fails if unclassified); run `npm run registry`.
3. Add it to at least one module in `modules/registry.json`; add templates when its phase is reached (M4+).
4. Run `npm run check`. Record material scope changes in `plan/SCOPE.md` and `DECISIONS.md`.
